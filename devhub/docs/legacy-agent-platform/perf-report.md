# 对话接口压测报告（2026-10-16）

> 环境：单机 Docker Compose（app `-Xmx768m` + MySQL + Redis + Milvus，宿主机 16GB Windows）
> 工具：`tools/loadtest/load_test.py`（Python stdlib，同步接口 POST /api/v1/chat 全链路：改写→检索→重排→生成→校验）
> 问题池：6 类知识库问题 × 递增变体编号（验证语义缓存与全链路两种路径）

## 结论

**未防护的系统在 100 并发下直接崩溃（Docker 引擎 OOM）；双层限流防护后，1700 QPS 洪水下零崩溃、零 5xx，放行请求全部成功。**

## 三轮对比

| 场景 | 并发 | 请求尝试 | 成功 | 失败 | 成功吞吐 | P50 | P99 | 系统状态 |
|---|---|---|---|---|---|---|---|---|
| ① 无防护（限流器禁用+引擎崩溃前） | 100 | ~1500 | 0 | 全部连接失败 | 0 | - | - | **Docker 引擎 OOM 崩溃**，需人工重启全栈 |
| ② 入口限流（每IP 15/s，LLM 并发禁限） | 10 | 112 | 112 | 0 | 1.66 QPS | 0.9s | 38.9s | 稳定；语义缓存吸收相似问题（P50 亚秒） |
| ② 同上 | 50 | 32,894 | 681 | 32,213（429） | 14.6 QPS | 1.0s | 3.6s | 稳定；单 IP 洪水被入口限流拦截 |
| ③ 完整防护（+LLM 信号量 20 并发/排队 45s） | 50 | 2,930 | 110 | 2,820（429） | 1.28 QPS | 20.0s | 66.1s | 稳定；放行请求 100% 成功，排队尾延迟可见 |
| ③ 同上 | 100 | 80,184 | 690 | 79,494（429） | 14.6 QPS | 1.1s | 5.3s | **稳定**；≈1700 QPS 洪水下 0 崩溃 0 5xx |

## 防护架构（双层分工）

1. **入口层 `ChatRateLimitFilter`**（Redis 固定窗口）：全局 120 rps + 每 IP 15 rps——拦截 HTTP 洪水，超限 429 秒拒，不进入昂贵管道。单 IP 压测场景下它是主要拦截者（3.2万~7.9万次拒绝）。
2. **管道层 `LlmCallLimiter`**（公平信号量 20 并发 + 45s 排队超时）：保护 LLM 供应商配额——无限制放行会在高并发下触发 429 连锁导致熔断器全开（全模型不可用）；排队超时返回"稍后再试"友好降级而非 500。

## 关键观察

- **有效吞吐的真实上限是 LLM 管道延迟**（全链路 20-40s/问），而非应用层——c=10 时 1.66 QPS 已是单实例饱和值；扩容需多副本 + 供应商配额同步提升
- **语义缓存是第一道"高并发"防线**：相似问题（余弦>0.95）亚秒返回，压测中 P50<1s 的部分全部来自缓存命中
- 分数归一化 bug 修复（LLM 重排 0-10 → 0-1）后，CRAG 门控（top1<0.5 拒答）恢复设计语义，spot 回归：正常题带引用回答、知识库外题正确拒答
- 崩溃根因：16GB 宿主机上 Docker WSL VM 内存上限被打满；生产环境需独立资源规划

## 已知限制（诚实清单）

- 压测为单 IP 来源，主要验证入口限流与系统存活；多 IP 均匀分布场景下信号量排队将成为主要瓶颈路径（已实现，未在此报告覆盖）
- SSE 流式接口未单独压测（同步接口已覆盖相同管道）
- 流式链路的 token 记账仍缺失（Reactor Context 传递未实现，@Async 路径已修复并有数据验证）
- `agent.llm.max-concurrent` 等参数可通过 `.env` 环境变量运行时调整（compose 已透传）
